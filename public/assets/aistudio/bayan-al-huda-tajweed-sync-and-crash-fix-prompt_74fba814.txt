BAYAN AL-HUDA - TAJWEED SYNC, PLAYBACK SPEED AND CRASH FIX

TASK TYPE: targeted bug fix inside the existing app. Do not redesign, rename, delete or disable anything that already works. Fix only what is listed below, and prove each fix with a real test.

HARD RULES
1. Never alter, rewrite, regenerate or re-diacritize Quranic Arabic or the tajweed annotation data. Highlight timing may be corrected; religious text may not.
2. Do not modify, re-encode, trim or replace any reciter audio file. Fix the player and the timing layer, not the recordings.
3. Do not remove any existing reciter, screen, button, bookmark, download or setting. The new reciter picker is additive.
4. No AI-generated Quran text, timing data or translations. Timing values must come from the actual audio file, a verified timing dataset or measured audio analysis.
5. Every fix must degrade gracefully. A missing file, a bad offset or a broken cache must never crash the app or blank the screen.

PART 0 - REPRODUCE AND MEASURE FIRST
Before changing code:
- Open a surah, enable Tajweed, press play, and record the actual playback rate reported by the player.
- Reproduce the Tajweed crash and capture the full stack trace, the surah/ayah, the reciter, the audio source and the gesture that triggered it (tab open, surah open, play, seek, speed change, rotation, background return).
- Inspect how reciters are registered, whether each reciter has Bismillah audio at surah start, and whether per-word or per-ayah timing exists at all.
- Inspect how the current highlight advances (fixed timer, ayah duration estimate, dataset timing, or scroll position).
- Note the exact current behaviour for the two newly added reciters versus the default reciters.
Report these findings before implementing.

PART 1 - FIX THE TAJWEED CRASH (HIGHEST PRIORITY)
Treat Tajweed as a non-essential presentation layer that can never take down the reader.
- Parse tajweed annotation files off the main thread, in a background dispatcher, with a streaming or chunked parser instead of one huge in-memory object. Cache parsed results by surah and edition.
- Validate every annotation on load: edition id and checksum match, surah and ayah exist, character start and end offsets are within the exact Uthmani text length, start is not greater than end, and rule category exists. Drop only the invalid entry and log it; never let an invalid entry reach the text renderer.
- Guard span construction with try/catch. Any exception while applying spans falls back immediately to plain Uthmani rendering and shows the tajweed toggle as temporarily unavailable, with the reader still usable and audio still playing.
- Add null, empty, truncated and corrupt asset handling: missing file, wrong version, half-downloaded file, stale cache and interrupted download must all resolve to plain rendering plus a short non-blocking notice.
- Lower memory pressure: no full-Quran annotation load on open, no duplicate copies of the annotation list per recomposition, no heavy work in onDraw or in list item binding.
- Stop the crash on rapid interactions: tajweed toggled while loading, surah switched mid-load, list scrolled off screen mid-load, screen rotated, app sent to background, seek during load. Use a single cancellable load job keyed by surah and edition, and ignore results for a surah that is no longer displayed.
- Verify offsets against the exact text edition, as already required, before any offset is applied.
Acceptance: tapping Tajweed, playing, seeking, switching surah, rotating and toggling rapidly must never crash the app.

PART 2 - FIX PLAYBACK SPEED
- The default playback rate must be exactly 1.0x on first use of every reciter and every surah, and after a fresh install or cleared data.
- Find and remove the cause of the ~1.2x behaviour: an explicit setPlaybackSpeed or PlaybackParameters value, a pitch-shifting library default, a persisted speed preference applied silently, a speed index mapping bug, or a second player instance started on top of the first. Report which one it was.
- Keep any user-chosen speed as an explicit, visible choice that never changes on its own. Store it per user setting, not per reciter, and reset any corrupt or out-of-range stored value to 1.0x.
- If a speed control already exists, keep it, clamp it to a safe range such as 0.5x to 2.0x and label it clearly. Never apply speed silently.
- When the rate is anything other than 1.0x, every highlight timing must scale by the same factor. Never mix a scaled player with unscaled timing.
- Verify that starting a new reciter or a new surah does not inherit a stale rate object.

PART 3 - BASMILLAH-AWARE ALIGNMENT (the reported mismatch)
Cause: the two new reciters recite Bismillahir Rahmanir Rahim before the surah body, and the default reciters do not, so the highlight runs ahead of the audio by the length of that Basmala. Handle this structurally:
- Record per reciter and per surah whether the audio includes a Basmala prefix. Apply it for every surah except Surah 1 (where the Basmala is ayah 1) and Surah 9 (where there is no Basmala).
- Never hardcode a fixed millisecond guess. Measure the Basmala segment from the actual audio of that reciter and surah: detect the first offset of the surah body with a voice-activity and onset analysis, or use a verified timing dataset for that reciter. Store the measured value in a calibration table keyed by reciter id, surah number, audio source, file duration and file checksum.
- Invalidate a calibration entry when the audio file, its duration or its checksum changes.
- Provide a deterministic fallback order: verified timing dataset for the reciter, then measured calibration, then a declared per-reciter Basmala duration from the reciter profile, then a conservative default. Log which path was used.
- Any ayah-level timing must be offset by the measured Basmala duration, and word-level highlighting must start at the shifted origin, so the first highlighted word appears exactly when the reciter starts the verse.
- Verify with the two new reciters on at least Surah Al-Fatiha, Al-Baqarah, Al-Kahf, Yaseen and Al-Mulk, and with a default reciter on the same surahs for contrast.

PART 4 - HANDLE REPEATS AND BACKTRACKING
The reciters sometimes return to a verse and recite it again. The highlight must follow the audio instead of marching forward.
- Do not run an independent forward-only timer. Drive the highlight from the actual playback position, and re-sync on every position update.
- When the measured position is behind the current highlight, move the highlight back immediately; never keep it ahead of the audio.
- When a verse is repeated, keep highlighting that verse until the audio truly moves on. Never auto-advance to the next ayah because a timer expired.
- Use light on-device audio analysis, such as silence gaps and energy or onset changes, only to refine the boundary between word and ayah positions. This analysis adjusts timing only; it never touches the text.
- Clamp the highlight inside the current ayah, and when confidence is low, hold the current word and show a subtle resyncing indicator instead of guessing wildly.
- Handle seek, pause, resume, buffering, audio focus loss, incoming calls, and headphone unplug without leaving the highlight stranded.

PART 5 - RECITER PICKER
- Make the current reciter name in the player bar a tap target that opens the existing style of bottom sheet listing every available reciter.
- Show every reciter already bundled or downloadable in the app, with Arabic and Latin names, a short label when offline audio is available, and a check mark on the current selection.
- Selecting a reciter switches playback from the current ayah, keeps the current surah and verse position, respects the user's downloaded or streamed preference, resets timing and calibration for the new reciter, and returns the rate to the user's saved setting or 1.0x.
- Keep the list scrollable, searchable if the app already supports search, accessible with correct RTL and LTR labels, and free of clipped or overlapping text. Show a clear unavailable state for a reciter whose audio or timing cannot be loaded, without hiding it.
- Do not duplicate an existing reciter selector if one already exists; extend it.

PART 6 - STATUS AND DIAGNOSTICS
- Add a small, unobtrusive indicator when timing is calibrated, when it is using a fallback, or when it is resyncing. No popups, no new screens.
- Write a local, redacted debug log for timing decisions and crash guards: reciter, surah, ayah, path used, offsets applied, and dropped annotations. Never log personal data or credentials.
- Keep a single switch to disable audio-assisted refinement, defaulting to on, so a user can test plain timing.
