BAYAN AL-HUDA - COMPLETE HADITH COLLECTION RESTORATION

MISSION
Audit the existing Bayan Al-Huda app, restore incomplete or incorrect Hadith data, and provide correctly matched Arabic, Urdu and English for each of the 19 listed collections. This is a real implementation task, not a mockup. Preserve existing application functionality and religious-text integrity.

NON-NEGOTIABLE RULES
1. Audit before editing. Mark each collection COMPLETE, PARTIAL, MISSING or BLOCKED. Work only on incomplete items; do not duplicate complete content.
2. Never fabricate, paraphrase, auto-translate, silently correct, renumber or substitute Quran, Hadith, commentary, translation or references. No AI-generated religious content.
3. Never attach translations by array position or row order. Match them through verified collection, edition and Hadith identities.
4. Preserve an immutable copy of every original dataset. Any approved replacement requires a backup, source comparison, migration plan, audit log and rollback path. Never silently overwrite existing records.
5. Do not delete, disable or redesign existing features, databases, collections, search, bookmarks, history, caching, offline access, Quran, Tafsir, prayer, audio or Sunni/Shia modules.
6. Inspect actual machine-readable source files and API responses, not just README claims. PDFs, scans and websites may guide verification, but final integrated content must be validated JSON or SQLite.
7. Verify copyright, licence and redistribution permission before importing or shipping data. If permission or reliable matching is unavailable, mark the item BLOCKED or PARTIAL and explain why. Never claim completion to meet a target count.

PART 2 - SECURE HADITHAPI CREDENTIAL HANDLING
The HadithAPI credential included with the request must be treated as exposed. Do not copy it into code, files, logs, reports, commits or this prompt. Rotate/revoke it with the provider before use and use only a newly issued credential.

HadithAPI endpoint base: https://hadithapi.com/public/api/hadiths/

Security requirements:
- Inspect the provider documentation to determine supported authentication. Prefer an authorization header if supported. If the API requires a query parameter, add it only in a trusted server-side request.
- The Android app must call a backend proxy that you control; the proxy retrieves the credential from a deployment secret manager or protected environment variable such as HADITHAPI_API_KEY. The proxy calls HadithAPI over HTTPS and returns only the required response.
- Never embed the credential in the APK, source code, GitHub, Gradle files, BuildConfig, strings.xml, assets, client-side .env files, screenshots, analytics or crash reports. A value packaged in an Android app is extractable and is not secure.
- Redact credentials from application, proxy, HTTP-client, CI and analytics logs; disable logging of authenticated request URLs; never cache credentials or include them in error messages.
- Apply server-side access control, rate limits, input validation, timeouts and safe error handling. Restrict the credential at the provider if possible. Document rotation and revocation.
- Use CI/deployment secret storage, not a committed configuration file. Add secret scanning and verify the credential is absent from the repository history and final APK.
- If no secure backend can be deployed, do not put the key in the app. Use other licensed sources or mark API-dependent work BLOCKED and explain the limitation.

7. Forty Hadith Qudsi: use verified Arabic-English JSON and Urdu for the exact same 40-Hadith compilation.
8. Sunan Sa'id ibn Mansur: reconstruct from verified sources. Obtain Arabic first, then reliable English and Urdu. Never substitute another Musannaf.

10. Sahih Ibn Hibban: identify the exact edition and arrangement; verify Arabic; add Urdu and English.
11. Al-Mustadrak ala al-Sahihayn: find complete structured Arabic and matching translations; preserve differing gradings with their sources.
12. Musannaf Abd al-Razzaq: obtain complete structured Arabic-English records and add verified Urdu.
13. Musannaf Ibn Abi Shaybah: treat the approximately 37,943-record dataset as a candidate; verify against the selected edition and add Urdu.
14. Sunan ad-Daraqutni: restore complete Arabic and locate structured Urdu and English.

For each collection preserve its exact title, selected edition and arrangement. Do not combine similarly named works or editions.

PART 4 - RECORD IDENTITY, TRANSLATION MATCHING AND REPAIR
Create a stable identity for each narration using:
- Collection ID and edition ID
- Original Hadith reference and alternative reference numbers
- Book and chapter IDs/names
- Stable source record ID, where available
- Original Arabic text
- Urdu and English text, each with translator and source
- Grading and its source, where documented
- Source URL, licence and verification state

Validate by identity, edition and references, then compare text. Detect previous/next-Hadith translations, +1/-1 offsets, missing or duplicate records, wrong chapters, partial translations, and similar but different narrations. Do not automatically repair uncertain matches; flag them for human review. Preserve disagreements and variant gradings with attribution.

Arabic replacement: when existing Arabic is substantially corrupted, compare the database with a complete verified machine-readable edition. Replace only records confirmed against the selected edition. Keep the old data in immutable backups and produce a record-level change report. Preserve numbering, chapters, references and edition metadata. Migrate bookmarks and user references safely; keep unresolved bookmark mappings intact and report them.

Translation policy: use a complete structured published translation where available. A scanned/printed edition may be digitized only with permission and must be checked before export. If no verified translation exists, mark it unavailable and report missing records. Never present machine-generated Urdu or English as a published translation. Apply the same verification policy to Arabic, Urdu and English.

PART 5 - DATA FORMAT AND APP COMPATIBILITY
Deliver validated application-ready JSON and/or SQLite, not a PDF or a list of links. Preserve source files unchanged and use a separate adapter/mapping layer for the app schema. Include UTF-8 validation, schema versioning, stable IDs, duplicate detection, record counts, completeness checks and database migrations. Preserve existing app architecture and all user data. Avoid unnecessary APIs and paid services.

Deliver the actual validated JSON/SQLite files and an integrity report with checksums. Do not claim a collection is complete unless its promised coverage is verified for the selected edition and translations are correctly matched. Clearly distinguish source coverage from translated coverage.

FINAL PRINCIPLE
Restore one collection at a time. Preserve originals, verify editions and sources, match each translation to its exact narration, respect licences, test the app, and report honestly. Existing functionality and religious-text integrity take priority over speed or record counts.
